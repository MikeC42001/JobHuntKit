**First CI run found 3 real cross-platform bugs (2026-08-05, PR #1):** `scripts/sync.sh` used
`mapfile`, a bash-4+ builtin absent from macOS's default bash 3.2 — every push silently failed
to build its audit file list there. `engine/lib.sh`'s `browser_flags()` only added
`--no-sandbox` under root, but GitHub Actions' ubuntu runners restrict the sandbox helper for
non-root users too, crashing headless Chromium (SIGABRT) — fixed by also checking `$CI=true`.

from Python on windows-latest CI resolves to Windows' own WSL launcher stub (errors out with no
distro installed), not Git Bash — test-harness-only, doesn't affect a real user already running
inside Git Bash. Fixing `bash_executable()`'s literal Git-for-Windows path also required adding
an `ABS_PATH_ALLOWLIST_PREFIXES` escape hatch to `audit_public.py`'s own absolute-path check —
generic Program Files install paths, no personal data, but still Windows-drive-letter-shaped.

**CI moved off the deprecated Node 20 runtime, 2026-08-10 — and the bump broke the macOS
renderer, which is the part worth remembering.** All four actions GitHub's warning named were
bumped to current majors: `checkout` v4→v7, `setup-python` v5→v7, `setup-node` v4→v7,
`browser-actions/setup-chrome` v1→v2. **v2 changed its `chrome-version` default from `latest` (a
Chromium snapshot) to `stable` (Google Chrome for Testing), and that binary hangs indefinitely on
macOS arm64 at `--print-to-pdf`** — the job reached step `[3/10]`, the first render, and sat
there 20 minutes until cancelled, while the same commit rendered fine on ubuntu. Fixed by
pinning `chrome-version: latest` explicitly, with a comment so nobody removes the
redundant-looking input later. Not a quoting problem despite the new path containing spaces;
`render_cv_minimal.sh` quotes `"$BROWSER"` correctly. The lesson: v2's *output* contract

## 2026-08-11 — the social card, and a wrong theory corrected by evidence

The custom social preview broke WhatsApp link previews: instead of the large banner GitHub's own
auto-generated card gets, the link rendered as a small square thumbnail, which crops a 2:1 card to
an unreadable fragment.

**The theory that was wrong: file weight.** GitHub's default card is a 1200x600 PNG at 46KB; ours
was 1280x640 at 268KB, and "chat clients skip heavy preview images" is a plausible and widely
repeated explanation. Two rounds of work went into it — a JPEG variant at 42KB, then a 128-colour
quantised PNG at 91KB — and the quantisation visibly damaged the card: the demo persona's avatar
lost its orange and the CV's bottom fade posterised into bands.

**What actually fixed it: dimensions.** At 1200x600 the large banner came back, with a *heavier*
file than the one that failed (319KB vs 268KB). Same content, same format, only the dimensions
changed — which rules weight out rather than leaving it ambiguous.

Worth keeping, because this is exactly the kind of thing that gets "optimised" back into a bug:
**do not trade the share card's dimensions for bytes.** `SHARE_SIZE = (1200, 600)` in
`.github/make_social_card.py` is load-bearing; the quality settings around it are not.

Also from this pass, measured against GitHub's own `repository-open-graph-template.png` (whose red
guides mark a safe zone of x 80..1200, y 80..560 on a 1280x640 canvas):

- The bottom tagline had been rendering at y 560..575 — straddling the bottom guide and running
  past it. It carries the one-line pitch, so it was the worst element to have cropped.
- The left column sat 2-4px outside the left guide.
- Type was enlarged twice (title 82 -> 106px) and the CV with it: at feed-thumbnail scale the
  original was far smaller than it looked at full size.
- The one-line pitch then came within 15px of the angled CV, close enough that the card's shadow
  read as a collision. Splitting it across two lines took the clearance to ~345px and reads
  better stacked under the subtitle.

## 2026-08-11 (later) — the leak gate now admits what it didn't look at

`v0.1.2` shipped (docs and repo metadata only), and the 1200x600 dark card was uploaded as the
social preview, which closes the card work.

That left the oldest item on the follow-up list: **`audit_public.py` only ever audited git-tracked
files.** `git_tracked_files()` is its whole input, so a file that exists on disk but isn't tracked
was invisible to it — and the output said nothing about that. `clean — 119 file(s) checked, 0
findings` reads like a statement about the directory when it is only a statement about the index.

The failure mode isn't hypothetical, and it isn't that something leaked. It's that the gate
answered a question nobody asked. Twice a file was put in place *specifically to be checked* — the
new social-card PNGs, and later a screenshot in `.github/` — and each time the run came back clean
without those files ever being opened. A gate that stays silent about its own scope is worse than
one that reports a smaller number, because the reassurance is indistinguishable from coverage.

**A warning, not a finding.** An untracked file is not part of the commit or push the gate is
protecting: the pre-commit hook scopes to staged files, `sync.sh push` scopes to manifest paths,
and `precommit_jobhuntkit.sh` deliberately runs the gate *after* staging for exactly this reason.
Failing on scratch files would train the reflex of routing around the gate, which costs more than
the blind spot did. So the default run's exit code is unchanged, and `--include-untracked` is
there when you want those files actually scanned rather than merely listed.

`--exclude-standard` on the `git ls-files --others` call is load-bearing and worth not
"simplifying" later: without it the warning lists every gitignored artifact — `produced/`, a stray
`generate-pdfs/` run, `__pycache__` — fires on literally every run, and becomes wallpaper.

The warning prints after the report in **both** outcomes, not only the clean one. A run that
failed on one file has precisely the same blind spot as a run that passed; attaching the notice to
success only would have rebuilt a quieter version of the same bug.

One accepted redundancy: `precommit_jobhuntkit.sh` already lists untracked files at staging time
and then runs the bare gate, so both lists now appear in a commit. They make different claims —
the wrapper's is "not staged", the gate's is "not audited" — and it's the second one that has been
misread, so both stay.

Five tests (suite 128 -> 133), including one pinning that explicit paths emit no warning: that's
the hook's and `sync.sh`'s path, and adding noise to every commit is the regression this feature
would most plausibly cause.
